\chapter{Implementación de la Solución Tecnológica}
\label{ch:implementacion}

\section{Introducción}
El presente capítulo describe las etapas de implementación de la solución propuesta, la cual integra una arquitectura de microservicios sin servidor (\textbf{Serverless}) en el \textit{backend}, un módulo de procesamiento en el borde (\textit{Edge Computing}) basado en la librería \textbf{MediaPipe} para la extracción de \textit{keypoints} en el dispositivo móvil, y un subsistema de entrenamiento de Inteligencia Artificial orquestado en la nube. Se detalla la configuración de los componentes en Amazon Web Services (AWS) y el despliegue mediante \textbf{AWS Serverless Application Model (SAM)}, justificando las decisiones de diseño para maximizar la escalabilidad, la robustez y la eficiencia de costos.

\section{Arquitectura Serverless (Backend)}
El núcleo de la gestión administrativa y de datos se implementó bajo un modelo Serverless. Esta elección permite la \textbf{escalabilidad granular}, donde cada función Lambda escala independientemente según la demanda, y optimiza los costos al aplicar un modelo de \textbf{pago por consumo} para las operaciones de baja frecuencia. Los componentes principales se ilustran en la Figura \ref{fig:arquitectura}.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.8\textwidth]{CAPITULOS/capitulo6/diagrama.png}
    \caption{Diagrama de Arquitectura de la Solución}
    \label{fig:arquitectura}
\end{figure}

La arquitectura administrativa se compone de tres servicios principales, gestionados por funciones AWS Lambda:

\begin{enumerate}
    \item \textbf{Servicio de Autenticación (\texttt{loginFunction})}: Maneja el inicio de sesión y la generación de \textbf{Tokens JWT}.
    \item \textbf{Servicio CRUD (\texttt{CrudFunction})}: Gestiona las operaciones de datos en DynamoDB para Usuarios, Roles y el Catálogo de Señas.
    \item \textbf{Servicio de Gestión de Archivos (\texttt{S3BucketManager})}: Administra la carga y eliminación de evidencias (imágenes/video) en Amazon S3.
\end{enumerate}

\section{Implementación de Base de Datos}
La persistencia de los datos se realiza en \textbf{Amazon DynamoDB}, un motor de base de datos \textbf{NoSQL} de tipo clave-valor. Esta elección fue estratégica debido a la necesidad de \textbf{baja latencia} para las consultas de la API y la \textbf{flexibilidad del esquema} requerida para el Catálogo de Señas. Se utilizó el modelo de facturación \textbf{On-Demand} (\texttt{PAY\_PER\_REQUEST}), garantizando la eliminación del aprovisionamiento de capacidad fija y optimizando el costo.

\section{Implementación del Módulo Móvil (\textit{Edge Computing})}
\label{sec:modulo_movil}
La aplicación Android (Kotlin) cumple la función de interfaz de usuario y de \textbf{módulo de preprocesamiento en el borde} (\textit{Edge Computing}). El preprocesamiento se realiza mediante la librería \textbf{MediaPipe}, que es la encargada de la extracción de \textit{keypoints} (puntos clave) de la pose y las manos en tiempo real.

\subsection{Vectorización y Normalización para el Modelo IA}
Para la entrada del modelo de \textit{Deep Learning}, se extrae un vector de características de 195 dimensiones por \textit{frame}, como se muestra en la Ecuación \ref{eq:input_vector}.

\begin{equation}
    V_{\text{input}} = [x_1, y_1, z_1, \dots, x_{65}, y_{65}, z_{65}, \text{progreso\_temporal}]
    \label{eq:input_vector}
\end{equation}

El vector de 195D se compone de:
\begin{itemize}
    \item \textbf{194 Dimensiones Espaciales:} Producto de la concatenación de \textit{keypoints} normalizados:
    \begin{itemize}
        \item 17 puntos de Pose (cuerpo/rostro) $\times$ 4 dimensiones ($x, y, z$, visibilidad) = \textbf{68 dimensiones}.
        \item 2 Manos $\times$ 21 puntos (dedos/palma) $\times$ 3 dimensiones ($x, y, z$) = \textbf{126 dimensiones}.
    \end{itemize}
    \item \textbf{1 Dimensión Temporal (\texttt{progreso\_temporal}):} Es un rasgo de ingeniería crucial que normaliza el tiempo de la seña en el rango $[0, 1]$, permitiendo que el modelo sea \textbf{invariante a la velocidad de ejecución} de la seña.
\end{itemize}

El cálculo del progreso temporal se implementa en la capa de procesamiento móvil, como se detalla en el Código \ref{code:kotlin_temporal}.
\begin{lstlisting}[language=kotlin, caption={Lógica Kotlin para Generación de Tensores con Canal Temporal (\texttt{DataProcessor.kt}) \label{code:kotlin_temporal}}, basicstyle=\ttfamily\small\bfseries]
// Fragmento de DataProcessor.kt
fun finalizeSequence(): List<FloatArray> {
  if (currentSignSequence.isEmpty()) return emptyList()

  val t_start = currentSignSequence.first().timestamp.toFloat()
  val duration = currentSignSequence.last().timestamp.toFloat() - t_start

  // Generación del vector 195D (194 espaciales + 1 temporal)
  return currentSignSequence.map { frame ->
    val timeProgress = if (duration > 0)
      (frame.timestamp - t_start) / duration else 0f
    
    // Se añade el canal extra al final del vector espacial
    frame.spatialData.toMutableList().apply { add(timeProgress) }.toFloatArray()
  }
}
\end{lstlisting}

\section{Implementación del Subsistema de Entrenamiento (MLOps)}
El entrenamiento de modelos profundos se separa de la arquitectura Serverless administrativa debido a las limitaciones de tiempo de ejecución y recursos de AWS Lambda. Se implementa una \textbf{arquitectura híbrida de orquestación (MLOps)} que utiliza AWS Systems Manager (SSM) y Amazon EC2 (con GPU).

\subsection{Configuración de la Función Orquestadora (AWS SAM)}

La función Lambda \texttt{trainingHandler} no ejecuta el entrenamiento, sino que sigue la siguiente secuencia orquestada:

\begin{enumerate}
    \item Verifica el estado e inicia la instancia EC2 (GPU) reservada si está detenida.
    \item Envía el comando de ejecución (\texttt{run\_training.py}) mediante el cliente SSM.
    \item El resultado del comando SSM (éxito/falla) es monitoreado por \textbf{CloudWatch Events} (o \textbf{EventBridge}), lo que permite una automatización posterior (e.g., apagar EC2 si la ejecución fue exitosa) o el envío de notificaciones.
\end{enumerate}

\subsection{Pipeline de Entrenamiento en EC2 (\texttt{run\_training.py})}
El script \texttt{run\_training.py} ejecutado en la instancia EC2 realiza el ciclo completo de MLOps de forma secuencial:

\begin{enumerate}
    \item \textbf{Sincronización (Data Freshness):} Ejecuta \texttt{download.py} para sincronizar los nuevos \textit{datasets} de \textit{keypoints} (archivos CSV) desde \textbf{Amazon S3} al almacenamiento local de la instancia EC2.
    \item \textbf{Preprocesamiento (Homogeneidad):} Ejecuta \texttt{data\_processor.py} para transformar los CSVs crudos en tensores de formato H5, aplicando la lógica de \textit{padding} y la \textbf{normalización temporal} descrita en la Sección \ref{sec:modulo_movil}.1.
    \item \textbf{Entrenamiento y Persistencia:} Utiliza el modelo construido por \texttt{model\_constructor.py} para entrenar la red Bi-LSTM. Durante esta etapa, se aplican \textit{callbacks} como \textbf{Early Stopping} para evitar el sobreajuste, y el artefacto final (modelo \texttt{.h5} o TFLite) es subido de vuelta a S3.
\end{enumerate}

\subsection{Arquitectura de la Red Neuronal}
Se utilizó una arquitectura recurrente bidireccional, optimizada para secuencias de longitud variable, definida por \texttt{model\_constructor.py}. La definición del modelo se muestra en el Código \ref{code:keras_model}.

\begin{lstlisting}[language=python, caption={Definición del Modelo de Bi-LSTM (\texttt{model\_constructor.py}) \label{code:keras_model}}, basicstyle=\ttfamily\small\bfseries]
# model_constructor.py
model = Sequential([
  Input(shape=(None, 195)),
  Masking(mask_value=0.0), # Ignorar padding
  
  # Capas Bidireccionales para contexto pasado y futuro
  Bidirectional(LSTM(64, return_sequences=True)),
  Dropout(0.2),
  
  # Agregación Temporal Híbrida
  Concatenate()([GlobalAveragePooling1D(), GlobalMaxPooling1D()]),
  
  Dense(64, activation='relu'),
  Dense(num_classes, activation='softmax')
])
\end{lstlisting}

Las decisiones arquitectónicas clave se justifican de la siguiente manera:

\begin{itemize}
    \item \textbf{Capa \texttt{Masking(mask\_value=0.0)}}: Es crucial para la \textbf{robustez a secuencias variables}. Permite a la red recurrente ignorar los \textit{frames} de \textit{padding} introducidos para uniformar la longitud de las secuencias, asegurando que solo los datos de la seña real contribuyan al cálculo de la pérdida.
    \item \textbf{Capa \texttt{Bidirectional(LSTM)}}: Maximiza la \textbf{comprensión contextual} de la secuencia. Al procesar la entrada en dos direcciones (de principio a fin y viceversa), la red aprende características que dependen tanto del movimiento precedente como del subsiguiente, esencial para la correcta identificación de señas dinámicas.
    \item \textbf{Agregación Híbrida de Pooling}: La concatenación de \texttt{GlobalAveragePooling1D} (media) y \texttt{GlobalMaxPooling1D} (máximo) crea un vector de características final que combina la \textbf{representación global} (promedio) con las características más \textbf{prominentes y distintivas} (picos) de la secuencia, mejorando el rendimiento del clasificador final.
\end{itemize}

\section{Conclusión del Capítulo}
La implementación de la solución se fundamenta en un principio de \textbf{separación de responsabilidades} (\textit{decoupling}) para garantizar la robustez y mantenibilidad. Se logró integrar exitosamente tres componentes de naturaleza diversa: una arquitectura \textit{Serverless} con DynamoDB para la gestión administrativa escalable y eficiente en costos; procesamiento en el borde (\textit{Edge Computing}) con MediaPipe para la captura y preprocesamiento de datos en tiempo real; y una infraestructura de cómputo dedicada (EC2/GPU) con orquestación Serverless para las tareas pesadas del ciclo de vida de la Inteligencia Artificial (MLOps). Este diseño híbrido demuestra una \textbf{solución tecnológica robusta}, mantenible y eficiente en costos operativos.
